# Blackwell 六路内部温度：从寄存器发现到独立验证

## 这份说明要回答什么

RTX 50 系列显卡内部显然掌握着比常规监控软件显示得更多的温度信息。问题是：哪些温度是 NVIDIA 驱动正式提供的，哪些是从硬件寄存器中发现的？那六个特殊地址为什么被认为与内部温度有关？我们又能否独立读出并验证它们？

下面按照发现和认证的顺序说明。

## 一、首先区分三类温度

| 温度 | 数据来源 | 公开程度 |
|---|---|---|
| GPU 核心温度 | NVIDIA 驱动，通过 NVAPI / NVML 返回 | 公开 |
| 显存温度 | NVIDIA 驱动，通过 NVAPI 返回 | 部分公开，实际可用性取决于显卡和驱动 |
| 六路内部温度 | 直接读取 GPU BAR0 中的固定 MMIO 寄存器 | 没有通过常规 NVIDIA 温度 API 公开 |

### GPU 核心温度

这是监控软件最常见的 `GPU Temperature`。NVIDIA 的公开 NVAPI 将它定义为 `NVAPI_THERMAL_TARGET_GPU`，应用程序正常调用驱动即可取得。

### 显存温度

显存温度同样是由 NVIDIA 驱动提供的。公开 NVAPI 中存在 `NVAPI_THERMAL_TARGET_MEMORY`，但这只说明接口模型支持显存温度，不保证每一代 GeForce 都会通过这个公共调用返回显存结温。

RTX 50 上，一些监控工具使用扩展 NVAPI 温度结构取得显存结温。相关入口仍然经过 NVIDIA 驱动，但属于未公开接口，不能当作拥有长期兼容承诺的公共 ABI。LibreHardwareMonitor 中可以看到[扩展 NVAPI 结构](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/master/LibreHardwareMonitorLib/Interop/NvApi.cs)和[架构相关的温度映射](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/blob/master/LibreHardwareMonitorLib/Hardware/Gpu/NvidiaGpu.cs)。

NVIDIA 的[公开 NVAPI 温度文档](https://docs.nvidia.com/nvapi/group__gputhermal.html)最多描述 3 个传感器，并没有公开下面这组六路内部温度。

### 六路内部温度

这六路数据不是向 NVIDIA 的温度 API 请求得到的，而是从显卡 BAR0 的固定 MMIO 地址读取。换句话说，它绕开了 NVIDIA 的遥测接口，直接查看 GPU 温度模块中的寄存器。

需要注意：这不等于 Windows 下完全不需要驱动。普通用户态程序无权直接映射 PCIe 设备的物理 MMIO，仍需由内核驱动执行受限的只读访问。

## 二、发现的六个地址

在已研究的 Blackwell GPU 上，六个连续的 32 位寄存器位于：

| 通道 | BAR0 偏移 |
|---|---:|
| 1 | `0xAD0A90` |
| 2 | `0xAD0A94` |
| 3 | `0xAD0A98` |
| 4 | `0xAD0A9C` |
| 5 | `0xAD0AA0` |
| 6 | `0xAD0AA4` |

目前采用的解释方式是：

- bit 30 表示该通道有效；
- 温度为 `(raw & 0xFFFF) / 256` 摄氏度；
- 六路有效温度中的最大值，作为实验性的 Hot Spot。

这些都是相对于 BAR0 的偏移，不是完整物理地址。BAR0 的实际基址由系统分配，不同电脑可能不同，因此不能照抄某台电脑的完整物理地址。

## 三、如何认证它们与内部温度有关

NVIDIA 尚未公开这六个寄存器的正式定义，因此这里没有一份厂商手册可以直接给出答案。现有结论来自多层证据相互印证，而不是依赖某一个人的猜测。

### 证据一：地址位于 Blackwell 的 THERM 模块

Linux nouveau 使用的、带 NVIDIA 版权声明的 GB202 头文件，将 `0xAD00BC` 定义为 `NV_THERM_I2CS_SCRATCH`。这确认了 `0xAD0000` 附近属于 Blackwell 的 `NV_THERM` 温度模块。

六个地址 `0xAD0A90–0xAD0AA4` 正好落在同一地址窗口中。[GB202 THERM 头文件](https://codebrowser.dev/linux/linux/drivers/gpu/drm/nouveau/include/nvhw/ref/gb202/dev_therm.h.html)

这一层证据能确认地址区域的用途，但还不能单独解释六个寄存器分别代表什么。

### 证据二：六个值具有温度应有的动态行为

六个寄存器连续排列、结构一致，并带有相同形式的有效位。按 `/256` 解码后：

- 数值落在合理的摄氏温度范围；
- GPU 加载后数值平滑升高；
- 负载结束和散热加强后数值平滑下降；
- 六路彼此接近，但并不完全相同；
- 最大值会随着不同区域的热状态变化。

这组行为很符合分布在芯片内部的多路温度通道，而不像计数器、状态字或随机数据。

### 证据三：数据格式符合 NVIDIA 的温度定点格式

NVIDIA 开源内核模块中的 `NvTemp` 使用带 8 位小数的定点格式，也就是以 `1/256°C` 为一个步进。

六路寄存器的低 16 位除以 256 后能够得到稳定温度，与 NVIDIA 自己使用的格式习惯吻合。[NVIDIA `NvTemp` 定义](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/570.144/src/common/sdk/nvidia/inc/nvfixedtypes.h#L1674-L1701)

这不能独立证明寄存器身份，但排除了许多不合理的解码方式。

### 证据四：Blackwell 确实采用多路 BJT / TSENSE 体系

NVIDIA 面向 Blackwell 平台公开的技术资料描述了多个 BJT/TSENSE 通道、每通道校准和选择最热温度的机制。这证明“Blackwell 芯片内部同时存在多路结温通道”符合实际架构。[NVIDIA T264/Blackwell 温度规格](https://developer.nvidia.com/docs/drive/drive-os/7.0.3/public/drive-os-linux-sdk/_downloads/08b4a1e13b3e6a08ddcba1418b3dc77f/SWE-BPMPFW-231-ICD__T264_BPMP-DTB_specification.pdf)

这份资料属于另一款 Blackwell 芯片，所以它不能直接证明桌面 GB202 一定使用相同地址和数量，但它为多路 BJT 的存在提供了架构证据。

### 证据五：外部研究得到相同地址和解码方法

igor'sLAB 的独立研究列出了完全相同的六个地址、bit 30 有效标记和 `/256` 解码方式，并将结果与 NVIDIA 内部诊断环境 MODS 进行比较。[igor'sLAB Blackwell Hotspot 寄存器研究](https://www.igorslab.de/en/blackwell-hotspot-ibhe-estimation-register-findings-download-nvidia-question/)

这说明发现不只存在于一台电脑或一个程序中。

### 辅助验证：与 HWMonitor 1.65.1 进行实时对照

HWMonitor 1.65.1 的官方版本说明写明，它修正了 RTX 50 Hotspot 的读取和解码。[HWMonitor 1.65.1 版本说明](https://www.cpuid.com/softwares/hwmonitor.html)

在同一台 RTX 5090 Founders Edition 上，我们将六路有效温度的最大值与 HWMonitor 1.65.1 实时并排观察。两边读数准确一致，并随着负载和冷却同步变化。

这项对照只能算**辅助验证**，不能列为寄存器身份的直接证据。HWMonitor 只是显示了读取结果，CPUID 并没有公开这些寄存器的厂商定义，也没有公布足以证明其物理含义的材料。

它仍然具有一定参考价值：CPUID 是长期从事硬件识别和监控软件的成熟机构，通常会在取得一定技术依据后才把新的传感器读取正式加入产品；1.65.1 的版本说明也明确感谢了参与 Hotspot 读取与解码研究的 PauloGomesTeam。由此可以合理推测，CPUID 在上线前进行过内部验证或获得了额外技术信息。但在这些依据没有公开以前，这只能增加结论的可信度，不能代替证明。

我们的实时对照进一步说明：这组六路地址可以被独立读取，采用当前有效位和解码方法能够复现 HWMonitor 1.65.1 的结果。它验证的是**地址和解码流程具有可复现性**，而不是证明每个地址一定对应某个具体物理传感器。

## 四、这些证据最终能证明到什么程度

目前可以很有把握地说：

- 六个地址位于 GB202 的 THERM 温度模块窗口；
- 在测试的 RTX 5090 Founders Edition 上，它们表现为六路有效温度通道；
- bit 30 与 `/256°C` 的解释能够得到稳定、合理的数据；

另外还有两项辅助结果：

- 六路最大值与 HWMonitor 1.65.1 的 Hot Spot 实时结果一致；
- 我们能够在不借用 HWMonitor 驱动和程序的情况下独立复现同一读取结果。

这两项辅助结果提高了地址和解码方式的可信度，但不改变证据边界。

但仍然不能把以下判断写成 NVIDIA 官方事实：

- NVIDIA 从未正式确认这六个地址就是六个独立的物理 BJT 传感器；
- 每一路在芯片上的具体位置尚不清楚；
- 寄存器值可能已经经过校准、偏移、筛选或聚合，不一定是完全未经处理的原始传感器数据；
- 六路最大值是否在所有状态下都等同于 NVIDIA 内部的 Hot Spot 或 `GPU_OFFSET_MAX`，没有公开定义；
- 不同 Blackwell 型号、非公版显卡、VBIOS 或后续架构可能拥有不同的传感器数量、有效掩码和寄存器布局。

所以，最准确的结论是：**这六个地址是高度可信、可以复现的 Blackwell 内部温度通道，但它们的完整物理语义尚未得到 NVIDIA 官方确认。**

## 五、普通开发者能否自行读取

技术上可以，但 Windows 不允许普通应用直接访问 BAR0。正规的实验流程需要：

1. 编写一个功能受限的只读内核驱动；
2. 使用 Windows Driver Kit 构建；
3. 使用正式签名，或在开发机上使用测试签名；
4. 测试签名环境需要关闭 Secure Boot；
5. 执行 `bcdedit /set testsigning on` 后重启；
6. 由管理员进程打开驱动设备并读取结果。

测试签名会降低系统的驱动签名保护强度，只适合专用开发机。实验结束后应卸载驱动、关闭 TESTSIGNING、重启，并重新启用 Secure Boot。

不应为了方便而使用来源不明的通用物理内存驱动。更安全的做法是让驱动只映射一个固定页、只读取六个固定寄存器，不接受用户传入的地址、偏移、长度或写入数据。

## 六、独立复现小程序

为了确认这套读取方法可以脱离现有监控软件独立复现，我们制作了一个实验项目：

**[dataindustry/CAT-5090-hotspot-monitor](https://github.com/dataindustry/CAT-5090-hotspot-monitor)**

它不依赖 CPU-Z、HWMonitor、WinRing0、RyzenAdj、LibreHardwareMonitor 或 Afterburner，由两部分组成：

- 一个最小、只读、测试签名的 WDM 驱动，只映射目标页并读取六个固定寄存器；
- 一个只使用 Python 标准库的轮询程序，解码六路温度并计算最大值。

当前版本固定面向实验机上的 RTX 5090 Founders Edition，并在加载前核对 PCI 设备与 BAR0 资源。地址不符合预期时会直接拒绝，而不是猜测或扫描物理内存。

这套程序已经完成端到端运行，并与 HWMonitor 1.65.1 实时交叉验证。它证明了读取地址和解码流程可以被独立复现，但没有为这些寄存器增加新的厂商级身份证明。它的价值在于：不借用现有监控软件驱动，也能通过正规的测试签名流程得到同一组温度结果。

具体构建、测试签名、安装、持续监控和卸载方法见项目的 `README.md`。
